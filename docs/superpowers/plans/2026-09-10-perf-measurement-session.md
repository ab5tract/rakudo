# Performance measurement session (after milestone 3): plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax. This is a MEASUREMENT plan: its deliverable is a findings doc and a ranked lever list, plus whichever knobs won (adopted as defaults on the spot).

**Goal:** Rank the optimization levers for the JVM backend from measurements on the milestone-3 state (rakudo `9bf93837ca`+, nqp `55bdee5b7`+), over three clocks: the CORE.c compile, cold start (and a green t/ subset through it), and hot dispatch.

**User decisions (2026-09-10):** measure first, then rank; the test workload is 2-4 already-green t/ subdirectories, never the full suite; single runs, no triplicates; any knob that measurably helps is adopted at once as the default for every later measurement (forward only); the order is compile lever, cold-start profile, green subset, loop baseline. Runtime performance ranks above compile time when a change trades one for the other (report which clock moved).

**What the research already established (2026-09-10, engine briefing in the session ledger):**
- Oracle GraalVM's auxiliary engine cache is NOT applicable: the module path `nqp/build/jvm/share/truffle/` carries community Truffle jars only (no `truffle-enterprise`), and the cache is a native-image feature. The reachable subset is one shared `Engine` for the two contexts (`nqp/nqp-truffle/src/main/java/org/raku/nqp/truffle/NqpCodeEngine.java:213` and `nqp/nqp-truffle/src/main/kotlin/org/raku/nqp/truffle/TruffleGrammarEngine.kt:210` each build their own, so `engine.CompilerThreads` applies twice) and real `Source` names (every program is named `"nqp-code"`, `NqpCodeEngine.java:32`).
- Cold `./rakudo-j -e 'say 1'` is 4.10 s; with `-Dpolyglot.engine.Compilation=false` 3.77 s (8 CPU-seconds saved, 0.34 s wall). Cold start is the serial load path (5.6 MB `CORE.c.setting.jar` read, LZ4, 6 MB meta decode, a CodeRef per block, deserialize); program text is decoded eagerly, program parsing is lazy at first call (`CodeEngine.kt:119-129`).
- The CORE.c compile has a named lever: a traced compile found 1880 s of Truffle compiler time, 733 s of it on 114 roots failing "code installation failed: code is too large" after 6.4 s each; `NQP_CODE_MAX_COMPILE` (`NqpRootNode.java:102-121`) already gates `prepareForCompilation` on program size and has never been measured. Also accepted by this GraalVM: `engine.Mode=latency|throughput`, `engine.MultiTier`, `engine.FirstTierCompilationThreshold`/`LastTierCompilationThreshold` (there is no `engine.CompilationThreshold`), `engine.DynamicCompilationThresholds*`, `engine.BackgroundCompilation`, `engine.CompilerThreads`, `engine.PartialBlockCompilation` (+`PartialBlockMaximumSize`), `engine.TraceCompilation`, `engine.CompilationStatistics` (prints only with `NQP_CODE_CLOSE_AT_EXIT=1`), `compiler.MaximumGraalGraphSize`, `compiler.InliningRecursionDepth`.
- Option plumbing: `RAKUDO_JVM_XOPTS='-Dpolyglot.engine.X=Y' ./rakudo-j ...` for a run; `JDK_JAVA_OPTIONS='-Dpolyglot.engine.X=Y'` for the eval server and for `make`/`rakudo-j-build` (it prints `NOTE: Picked up JDK_JAVA_OPTIONS` on stderr per JVM start; never parse stderr's first line then). `rakudo-eval-server` exports `-Dpolyglot.engine.Compilation=false` to spawned children (override with `RAKUDO_JVM_CHILD_XOPTS`). A bad option surfaces through `rakudo-j` as an opaque `ExceptionInInitializerError`: probe an option set first through `org.raku.nqp.truffle.NqpCheck` on the same module path + `nqp-runtime.jar:nqp-truffle.jar:kotlin-stdlib:fastutil` classpath (seconds).
- `NQP_CODE_CALLSTATS` and `NQP_INVOKE_TRACE` no longer exist. Surviving: `NQP_DISPATCH_STATS=1` (folded hits / boundary invokes at exit), `NQP_CODE_TRACE/WHY/BAIL/STRICT`, `JESP_TRACE_CLASSLIB`, `NQP_CODE_MAX_COMPILE`, the Truffle trace options above; JFR via `RAKUDO_JVM_XOPTS=-XX:StartFlightRecording=...` and `jfr print --events jdk.ExecutionSample --stack-depth N`.
- Tooling: `tools/build/dice-spectest.raku` (per-file wall times through one warm eval server), `tools/build/evalserver-sweep.raku`, `tools/build/watched-run.raku` (`--show-file`, `--follow`), `docs/bench/jesp/plusquick.raku` (5 M warmup + 40 M `$a + $b`, prints ns/op), `docs/bench/jesp/resume-smoke.raku` (correctness, not a benchmark). No JFR scripts exist: write the summarizer in Raku under `tools/build/`.

## Task 1: The CORE.c compile lever

**Workload:** the CORE.c compile standalone, from the Makefile's own recipe: `make -n blib/CORE.c.setting.jar` prints the `rakudo-j-build ... --target=jar --output=blib/CORE.c.setting.jar ... CORE.c` command; run that under watched-run (`--log=.../corec-<label>.log --show-file=.../corec-<label>.markers --show='Stage'`), with `--output` redirected to a scratch path so `blib` stays the built state. One run per configuration.

- [ ] **Step 1: the baseline trace.** `JDK_JAVA_OPTIONS='-Dpolyglot.engine.TraceCompilation=true -Dpolyglot.engine.CompilationStatistics=true' NQP_CODE_CLOSE_AT_EXIT=1` on the standalone compile. Record: wall clock and the stage times (`Stage parse/optimize/qast/jast/...` lines), the count of `opt failed ... code is too large` roots and their mean compile time, total compiler time from the statistics block. This is the reference the knobs are judged against. Write a Raku summarizer `tools/build/truffle-trace-summary.raku` (input: the log; output: compiles / failures by reason / mean time / top-20 roots by compile time) and smoke it on a 30 s `rakudo-j -e` run first.
- [ ] **Step 2: `NQP_CODE_MAX_COMPILE`.** From Step 1's trace, take the wire size of the smallest failing root (the trace names roots; `NQP_CODE_WHY=1` on a runtime compile or `NqpRootNode.programSize` in the trace line gives sizes) and set `NQP_CODE_MAX_COMPILE` just below it. One compile. If wall clock drops, adopt: export it in `rakudo-j-build.in` and `Makefile.in` (build side) and consider `$jopts` (runtime side) separately, since a huge root that never compiles also never speeds up at runtime; report both clocks.
- [ ] **Step 3: `engine.PartialBlockCompilation=true`** (with the threshold from Step 2 removed, so the big roots get split instead of skipped). One compile. Adopt whichever of Step 2/3 is faster; if both help, combine.
- [ ] **Step 4: one shared Engine.** Code change (Kotlin/Java, runtime-only, ~20 s jar rebuild): build one `Engine` (`Engine.newBuilder().allowExperimentalOptions(true)`) in a shared holder and pass it to both `Context.newBuilder(...).engine(engine)` sites. Then `engine.CompilerThreads=<cores/2>` and `engine.Mode=latency` as two more single compiles, each adopted if it wins. Do not touch `contextPolicy`.
- [ ] **Step 5: record.** A table of configurations vs wall clock, stage times, compiler time, failed-root count, in `docs/jvm-perf-findings-2026-09.md` (new), and the adopted defaults committed.

Record the table; no code changes in this task beyond the summarizer.
