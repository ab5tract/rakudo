### Issues

#### Critical (Must Fix)

**C1. `is_inlinable` lost its table; the built CORE setting neither inlines routines nor lowers native arithmetic.**
`nqp/src/vm/jvm/QAST/Compiler.nqp:216-223` (`is_inlinable`) answers `%core_inlinability{$op} // 0`, and `%core_inlinability` is now written only by `map_classlib_core_op` (`:229`) - 626 classlib rows. Before (nqp `55bdee5b7:src/vm/jvm/QAST/Compiler.nqp`), `add_core_op($op, $handler, :$inlinable = 1)` at `:295-297` seeded 1 for every hand-mapped op and `map_jvm_core_op` (`:336-340`) went through it: 64 such calls, covering `add_i`/`sub_i`/`mul_i`/`add_n`/`mul_n` (`:2628` region), `if`, `while`, `list`, `stmts`, `bind`, `callmethod`, `defor`, `ifnull`, `xor`, `for`, the loops, `control`... Every one of those now answers 0. The consumer is RakuAST (`src/Raku/ast/code.rakumod:3300-3301`, `IMPL-INLINE-INFO` dies "Non-inlinable op encountered"), so the setting was compiled with routine inlining and native lowering off. Verified mechanism, not just symptom: the milestone gate's four red files (t/08-performance 22, 29, 32; t/02-rakudo/native-return-coercion.t) assert exactly those two things, and `native-return-coercion.t` shows it is user-visible semantics (boxing), not only speed.
*Why Critical:* it is a runtime-performance regression baked into every Rakudo jar on disk, on the user's stated top priority, and it invalidates the milestone's own timing points (make 1103 s, CORE.c 472 s were measured with the inliner idle, so they are not comparable to the milestone-3 baseline) as well as item 4's planned measurement session.
*Root cause is a plan defect, not an implementer slip:* plan ruling `docs/superpowers/plans/2026-09-10-jvm-unit-artifact-milestone-4.md:39` states the tables are "fed by `map_classlib_*_op(:inlinable)` and by `register_op_desugar(:inlinable)`", forgetting that `add_core_op`'s default was the bulk of the table. The Task 1 reviewer caught the twin (`supports_op`) but not this; a five-line registry probe would have.
*Fix shape (compiler-side: nqp clean build ~4 min + Rakudo make ~20 min):* in `Compiler.nqp` next to `:199`, a `%core_noninlinable` table seeded from the deleted `add_core_op(... :!inlinable)` names - exactly these twelve, from the old file: `call` (:1731), `callstatic` (:1732), `dispatch` (:1819), `syscall` (:1822), `register` (:1825), `delegate` (:1828), `track` (:1831), `guard` (:1834), `handle` (:1891), `handlepayload` (:2044), `usecapture` (:2275), `savecapture` (:2285). The classlib `:!inlinable` rows survive unchanged (current `:498-500` throwpayloadlex/throwpayloadlexcaller/lastexpayload, `:505-515` ctx/ctxouter/ctxcaller/ctxcode/ctxouterskipthunks/ctxcallerskipthunks/curcode/callercode/ctxlexpad/curlexpad/lexprimspec). Then `is_inlinable($hll, $op)` becomes: HLL override if present (as now, `:217-221`); else `%core_inlinability{$op}` if the key exists; else 0 if `%core_noninlinable{$op}`; else `QAST::TruffleEncoder.supports_op($op) ?? 1 !! 0` (the same "registry or encoder row" rule `core_op_supported` uses at `:243`). This reproduces the old semantics: every op the backend can compile is inlinable unless named, unknown ops are not. `callmethod` stays inlinable (it had no `:!inlinable` before; MoarVM's table agrees).
*The Rakudo half is mandatory, not optional:* `src/vm/jvm/Raku/Ops.nqp` lost five `add_hll_op('Raku', ..., :!inlinable)` rows - `p6bindsig` (old `:58`), `p6trybindsig` (`:82`), `p6decontrv` (`:166`), `p6decontrv_6c` (`:167`), `p6return` (`:178`). Today they answer 0 only because the table is empty; all five are in the encoder's `$extra_ops` hand list (`TruffleEncoder.nqp:56-62`), so the fallback above would make them inlinable, and an inlinable `p6return`/`p6bindsig` is a correctness bug (the op acts on the wrong frame). Add five `$ops.set_hll_op_inlinability('Raku', ..., 0)` lines after `my $ops := ...` (`Raku/Ops.nqp:47`). `p6trialbind` (`:!inlinable` via `register_op_desugar`) and the classlib `:!inlinable` rows (`p6capturelex`, `p6capturelexwhere`, `p6stateinit`, `p6getouterctx`, `p6captureouters2`) are already right.
*Verification before the make:* `NQP_CODE_RUN` unset, `nqp/nqp-j -e 'say(nqp::getcomp("QAST").operations.is_inlinable("Raku","add_i"))'` and the same for `if`, `while`, `list`, `callmethod` (1), `call`, `handle`, `p6return`, `p6bindsig`, `ctx` (0). Then the four red files. Add that probe as a permanent test (see Recommendations).

**C2. `("aa".."ac").elems` hangs - reproduced; the fault is confined to CORE.c's build of `SEQUENCE`.**
Reproduced: `timeout 60 ... -e 'say ("aa".."ac").elems'` -> rc 124. Shape, from probes on the built runner:
- `("aa" ... "ac")` prints `(aa ab ac ac ac ac ...)`; `("aa","ab" ... "ad")` and `("a" ... "c")` are correct. A pull-one loop on the range's iterator yields `aa ab ac ac ac`.
- The two-character case is the `$a.codes == $endpoint.codes` branch of `src/core.c/Rakudo/SEQUENCE.rakumod:121-129`: per-character sequences `$("a" ... "a")`, `$("a" ... "c")` crossed with `[X~]`. The inner `"a" ... "c"` gather (`:286-289` producer `unisuccpred`, loop `:325-350`) takes `c`, then its `$stop = 1` (`:344`) never terminates `until $stop`: `@tail` was not pushed on the accepted branch, so the producer yields `c` from `["b"]` again, forever; the cross product turns that into `ac ac ac`. The isolated inner sequence terminates (`(a b c)`), and so does `flat [X~]` at top level and a hand-written nested gather with a native `int` stop flag written after a resumed `take`.
- **Decisive:** a verbatim copy of `SEQUENCE.rakumod` renamed `MYSEQ`, compiled by the same compiler on the same runtime jars, terminates correctly both as a script (`Seq.new(MYSEQ("aa","ac")).head(6)` -> `(aa ab ac)`) and as a precompiled module (`use MySeq` with a `.precomp` cache, i.e. a comp-mode unit) -> `(aa ab ac)`.
*What that rules out:* Tasks 8 and 9 as the sole cause (runtime-only changes would hit the copies too; by reading they are also behaviour-preserving on this path: no frame with an exit handler is involved, `take` is an `EX_BLOCK` handler that returns through `ResumeException` before `giveBackTornFrames` (`ExceptionHandling.kt:293-305`), and no fused op calls user code inside `SEQUENCE`'s loop, so no finisher is ever built); the non-inlined code shape per se (the copies are compiled with the same idle inliner and work); Task 10 for this routine (`SEQUENCE`, `GATHER`, the producer closures and `succpred`/`unisuccpred` carry no parameter default or `where`, so the prologue scratch list is empty and the appended loop at `TruffleEncoder.nqp:1195-1198` is a no-op).
*What remains:* something specific to the CORE.c build of this routine - the setting's compile environment or the size/shape of the unit - i.e. Task 1's driver on its comp-mode-only paths (qbid pre-seeding, the orphan blocks compiled under the deserialize wrapper and therefore with the wrapper as outer, `Compiler.nqp:1455-1466`; the static-lexical rows now built after the wrapper compiles, `:1519-1531`; `cuid` blanked on comp-mode records, `:1766`), or a CORE.c-only consequence of C1 that a module compile does not reproduce. The runtime-jar bisection the ledger rules (Tasks 8/9) is therefore the wrong first experiment.
*Best single hypothesis:* a driver-side difference in how CORE.c's block records are built for this routine's inner blocks (outer qbid or static-lexical rows), since the program text of the loop itself is produced by an encoder path the working copies share.
*Cheapest confirming experiment, no build:* dump and diff the inner gather block's record and program between `blib/Perl6/CORE.c.setting.jar` and the precompiled `MySeq` jar (`/tmp/claude-1000/m4lib/.precomp/...`): `UnitZip.read(bytes)` gives `meta.blocks[qbid]` (name, outer, oLex/iLex, handlers, file, line - the block is anonymous but carries `SEQUENCE.rakumod:60`) and `programs[programIndex]`; a jshell session over `nqp-runtime.jar` plus the third-party jars does it in a few lines. Identical program text with different records points at the driver; different text points at the encoder in the setting's environment; identical both points at loading (`applyStaticLexValues`, outer resolution). Second experiment, free: re-run the reproducer after C1's make; if it disappears, C2 was a CORE.c-only consequence of C1 and still needs the dump to explain why the module build was immune. Only if both fail: the runtime-jar bisection (nqp `d8116d7c9` first, then `14df06863`, ~30 s each plus an eval-server restart), which by the evidence above should show the hang persisting.
*Why Critical:* a hang in every multi-character `Str` range and sequence, user-visible, and it stalls any sweep of `t/02-rakudo` on these jars.

#### Important (Should Fix)

**I1. `CallFrame.leave()`'s `alreadyLeft` guard silences the exit handler of any frame captured in a continuation** (`CallFrame.kt:461-471`). The engine's save path calls `cf.leave()` on every frame it packs into a continuation (`NqpCodeEngine.java:205-207, 215, 227, 241`), which sets `left`. Before Task 8 the handler ran on every `leave()` (at each `take` with the caller's stale return register as the resultish, plus once at the real exit); now it runs exactly once, at the first save, with that stale resultish, and never at the real exit. So `gather { LEAVE say "done"; take 1; take 2 }` fires `done` before the second `take` instead of after the block ends, and a `KEEP`/`UNDO` in a gather body decides on garbage. Both old and new are wrong; the new one is worse because the final, correct run is gone. Fix: the save road must not count as the exit for handler purposes - give the save sites a `leaveSuspended()` (count and `curFrame` only) or reset the frame's handler flag on resume; keep `left` as the torn/normal one-shot. Add the gather probe as a regression test beside `keep-undo.t`. Not covered by any gate that ran.

**I2. `UnitLoader.load(tc, filename)` marks a unit loaded before the load succeeds** (`UnitLoader.kt:67`): `loadedUnits.add(filename)` precedes the sniff and `loadAndRun`, so a load that dies (a missing or corrupt artifact, or a die inside the deserialize block) is silently a no-op on every later `nqp::loadbytecode` of the same path, and the failure surfaces later as an unrelated missing symbol. Add to the set after `loadAndRun` returns, or remove it on the exception path.

**I3. The `$extra_ops` list acquires a third role with the C1 fix.** It is already the survey's hand list and `supports_op`'s authority (`TruffleEncoder.nqp:56-62`, `:520-535`), and a name handled in `encode_op`'s `$name eq` chain but absent from the list makes both `supports-op` and (after C1) `is_inlinable` answer "no" for an op the encoder compiles. Give the list one name and one comment that states all three consumers, and pin it with a test (a `t/nqp` file asserting `supports-op` for every hand-row name; see Recommendations). Fix alongside C1 since that change touches the same file.

**I4. Milestone timings are invalid until C1 is fixed.** Task 7/10's "make 1103-1185 s, CORE.c 472 s vs baseline 475" were produced with the inliner idle in the setting compile, so they are not the milestone's baseline; the docs (`docs/jvm-truffle-only-plan.md` row 6, the spec's Done section) present them as such. After the C1 make, re-record and mark the old numbers as taken under the regression.

**I5. Missing regression test for the param-default shape Task 10 fixed.** `TruffleEncoder.nqp:1183-1198` fixes both the `where` and the default case; only the `where` case has a test (`t/02-rakudo/begin-time-attributive-param-method.t`). Add `BEGIN { sub g($x = { 42 }) { $x() }; say g() }` -> `42` as test 6 of that file (`plan 5` -> `plan 6`); no build needed, the file already runs green.
